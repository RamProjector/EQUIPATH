# EquiPath development setup

## Current status

This is an early foundation, not a complete application. It includes the public landing page, a deliberately limited API health endpoint, a supplementary WinForms API-connectivity screen, relational database migrations, credential verification, HTTP session endpoints, login throttling, and server-side authorization primitives. Application listing and draft creation APIs are implemented. Protected PDF evidence upload/download, coordinator-only screening and evaluator-assignment APIs, and recipient-scoped notification APIs are present. The web landing page includes a session-backed sign-in form, private notification inbox, applicant draft/status/document workspace, evaluator scoring and recommendations, assessment scheduling/results, and approver decisions; coordinator screening and evaluator-assignment queues, rubric configuration and registrar integration are not implemented yet. The evaluator scoring, credit recommendation submission, assessment scheduling/results, and approver decision workflows are partial implementations.

Do not use real applicant records or portfolio documents in this scaffold.

## Web stack (proposal-aligned)

1. Install a current XAMPP distribution with PHP and MySQL/MariaDB.
2. Copy the repository's web directory to xampp/htdocs/equipath.
3. Start Apache and MySQL in the XAMPP Control Panel.
4. Create a fresh development database, then import database/migrations/001_initial_schema.sql followed by database/migrations/002_authentication_rate_limits.sql using phpMyAdmin's Import tab.
5. Open http://localhost/equipath/public/ and check http://localhost/equipath/api/health.php.

Migration 001 creates the equipath_eteeap database if it does not exist and creates 23 core relational tables. Migration 002 adds the authentication rate-limit table. Neither migration seeds users or contains DROP statements. Apply migration 001 only to a fresh development database, then apply later migrations in order. A migration file is not a backup or a production migration plan; schema upgrades must be versioned and reviewed.

Configure DB_HOST, DB_PORT, DB_USER, DB_PASSWORD, DB_NAME, and a random AUTH_RATE_LIMIT_SECRET (at least 32 characters) in the PHP process environment before using the authentication endpoints. Keep these values out of source control and use a least-privilege database account. The CSRF bootstrap endpoint is GET /api/csrf.php; submit JSON credentials by POST to /api/authenticate.php with the returned token in the X-CSRF-Token header; POST to /api/logout.php with the current CSRF token to sign out. GET /api/applications.php returns at most 50 applications owned by the signed-in applicant and/or assigned to the signed-in evaluator. It requires an active account with an applicant or evaluator role, and checks ownership/assignment for each returned application. POST /api/create-application.php creates a draft for an active program and an application period whose status is open and current time is within its configured window. GET /api/application-options.php is applicant-only and returns active programs with active document requirements plus application periods currently marked open and within their date window. The applicant workspace uses this endpoint to avoid presenting closed periods as available; the create endpoint remains the authoritative validation. GET /api/application-documents.php?application_id={id} returns only document metadata for an application owned by the signed-in applicant; it deliberately omits storage keys and digests. The applicant UI lists owned applications, creates drafts, shows document versions and review status, uploads/downloads private PDFs through the existing protected endpoints, and offers a separate submission action. Send JSON containing integer `program_id` and `period_id`, plus the current `X-CSRF-Token` obtained from GET /api/csrf.php. The endpoint derives applicant identity from the authenticated session, generates the application number server-side, and transactionally writes the draft and initial status history. The service has MySQL integration coverage for owner/status persistence, history, and rejection of inactive programs or closed periods. POST /api/submit-application.php is applicant-only and CSRF-protected. It accepts JSON `{application_id}` and allows only an owned draft or application returned for correction. The service locks the application row, requires active required-document configuration, verifies every required requirement has a latest PDF version whose review status is `pending` or `accepted`, and rejects missing or latest-rejected/replacement-requested versions. It requires at least one active coordinator, then transactionally marks the application `submitted`, sets `submitted_at`, records status history and an audit event, and notifies active coordinators. A submission failure rolls back all database side effects. The client asks for confirmation and renders missing requirement names returned by the server. MySQL integration tests cover missing requirements, latest-version rejection, successful submission, history, audit and coordinator notification; HTTP guard tests cover method and CSRF rejection. This does not replace coordinator screening or make the submitted evidence malware-scanned. GET /api/screening-candidates.php is coordinator-only and lists submitted, screening, and needs-correction applications with document counts and required-evidence completeness indicators. GET /api/application-documents.php?application_id={id} exposes metadata to the owning applicant or a coordinator while the application is in the screening/correction queue; it never returns storage keys or digests. GET /api/application-history.php?application_id={id} is applicant-only and returns status transitions plus applicant-facing screening feedback only for the owning applicant; it does not return reviewer user IDs or internal staff-only data. The applicant document panel displays this timeline and feedback. Integration tests cover owner isolation, status timeline and feedback; HTTP guards cover method and identifier validation. POST /api/review-application-document.php is coordinator-only and CSRF-protected; it can accept, reject, or request replacement for a pending latest document version that still matches an active program requirement. Rejecting or requesting replacement moves submitted/screening applications to needs_correction and notifies the applicant; every review is audited. Coordinators can download evidence through GET /api/download-document.php only while the application is in the screening/correction queue; applicant ownership and evaluator assignment rules remain enforced for their respective roles, and administrator access is not implicit. The screening endpoint accepts eligible, ineligible, or needs-correction outcomes. An eligible outcome is rejected unless the program has active required-document configuration and every required requirement has an accepted latest PDF version. Screening outcomes and document reviews write status history where applicable, audit events, and applicant notifications transactionally. Feedback entered in these actions is applicant-facing. Integration tests cover latest-version review, status transitions, notifications, audit and invalid states; HTTP guard tests cover method, authentication and CSRF rejection. POST /api/assign-evaluator.php accepts positive integer `application_id` and `evaluator_user_id` values plus the current CSRF token; it is coordinator-only, requires an active evaluator account, rejects self/duplicate assignments and non-eligible application states, and transactionally writes assignment, status history, audit and notifications. The integration test covers assignment persistence, invalid cases and notifications; the HTTP guard test covers method and CSRF rejection. GET /api/evaluator-assignment-options.php is coordinator-only and returns applications in `eligible` or `under_evaluation`, active evaluator accounts, and current assignments for those applications. The web workspace filters already-assigned evaluators from each application's selection and shows assignment state. POST /api/assign-evaluator.php remains authoritative and rejects duplicate/self assignments, inactive/non-evaluator accounts and invalid application states. Integration tests cover the assignment transaction; HTTP guard tests cover method/CSRF on the write endpoint and authentication/method restrictions on the options endpoint. Workload caps and reassignment/cancellation workflows are not implemented. GET /api/rubric-management.php is coordinator-only and returns active programs, rubric versions, and criterion definitions. POST /api/save-rubric.php accepts `program_id`, `rubric_name`, and a `criteria` list, validates unique criterion codes and numeric score/weight bounds, then creates a new immutable version and audit event in one transaction. The previous active version is archived only in the same transaction as the new version. Rubric changes are blocked if multiple active rubrics exist or any application in the program is `under_evaluation`, preventing unfinished assignments from switching scoring criteria. Existing rubric criteria are never overwritten. Integration tests cover initial/versioned creation, exactly one active rubric, duplicate-code rejection, in-progress protection and audit; HTTP guard tests cover method, authentication and CSRF. GET /api/reports.php and GET /api/export-report.php are restricted to coordinator, approver, or registrar roles. Both accept optional `from` and `to` ISO dates, default to the most recent 90 calendar days, and reject inverted/invalid ranges or ranges longer than 366 calendar days. The dashboard reports aggregate application status/program counts, monthly submissions, screening outcomes, evaluator assignments, assessment events, accreditation decisions, and current non-superseded approved-credit totals. CSV output neutralizes formula-like text cells and excludes applicant names, email addresses, document metadata, and storage identifiers. Integration tests cover range validation, aggregate label preservation, formula-safe export and omission of identity fields; HTTP tests cover method and authentication guards. Additional report definitions and reconciliation against registrar exports remain future work. POST /api/save-evaluation.php accepts `evaluator_assignment_id`, `rubric_id`, a list of criterion `scores`, and a boolean `submit`; it is evaluator-only and verifies assignment ownership, application state, active program rubric, criterion membership, duplicate criteria, score maxima, feedback limits and complete criterion coverage before submission. Drafts remain editable; submitted evaluations are locked, audited, and notify active coordinators. The returned weighted percentage is a calculated evaluation result, not an accreditation decision or approved-credit record. POST /api/submit-credit-recommendations.php accepts one or more course recommendations for a submitted evaluator assignment; the assigned evaluator must own the assignment, the application must be in a permitted workflow state, course codes must be unique for the assignment, credits must be non-negative decimals with at most two places, and every recommendation requires a rationale. The transaction stores all recommendations together, writes an audit event and notifies active coordinators. GET /api/credit-recommendations.php returns recommendations only to the assigned evaluator or an authorized coordinator/approver. The evaluator workspace offers a separate credit recommendation form; existing recommendations are read-only and additional unique course codes can be submitted. Recommendations are not approved credits or a final accreditation decision. Integration/security tests cover ownership, duplicate handling, validation, audit and notifications. GET /api/accreditation-candidates.php is approver-only and lists applications awaiting a decision or with an existing decision eligible for explicit supersession. GET /api/accreditation-decisions.php?application_id={id} returns the applicant's current official decision or the full decision history to coordinators/approvers; application ownership is checked for applicants. GET /api/application-credit-recommendations.php?application_id={id} is coordinator/approver-only. POST /api/record-accreditation-decision.php is approver-only and CSRF-protected. A first decision requires `awaiting_decision`; a replacement must explicitly identify and supersede the current decision, preserving history rather than overwriting it. Approvals must include at least one course credit matching a submitted recommendation for that application, and approved credits cannot exceed the recommendation amount for the matching course title. Rejected, deferred, and returned-for-revision decisions cannot include approved-credit rows. Approved/rejected/returned decisions update application status and history; deferred decisions keep the application awaiting decision. Every decision is audited and notifies the applicant. The approver UI requires an explicit supersession confirmation and distinguishes recommendations from approved credits. Integration/security tests cover approval, recommendation-bound credits, supersession, state transitions, audit, notifications and HTTP guards. Result correction history beyond explicit decision supersession, applicant correction/resubmission UI, and registrar integration remain future work. GET /api/evaluation-assignments.php returns only the signed-in evaluator's active assignments and indicates whether the program has exactly one active rubric. GET /api/evaluation-rubric.php?evaluator_assignment_id={id} returns criteria and saved draft scores only to the assigned evaluator; it rejects submitted assignments, missing/ambiguous active rubrics, and rubric-version mismatches. The web workspace includes an evaluator assignment queue, score/feedback form, draft save and final submission controls. MySQL integration tests cover draft/save/submit, weighted calculation, ownership, bounds, completeness, audit, notifications and post-submit locking; HTTP guard tests cover method, authentication and CSRF rejection. GET /api/assessments.php returns assessment schedules and recorded results only for the signed-in applicant's own applications, the evaluator's assigned applications, or all applications for an authorized coordinator. GET /api/assessment-eligible-applications.php is coordinator-only and lists applications whose active evaluator assignments are all submitted or that already have an assessment schedule. POST /api/create-assessment.php requires a CSRF token and coordinator role, validates future start/end times, requires at least one active evaluator assignment and all active evaluations submitted before the first schedule, permits additional events only after the application is `assessment_scheduled`, and updates application status/history transactionally, audits the action, and notifies the applicant. POST /api/record-assessment-result.php is coordinator-only, permits a first result only after the event's scheduled end time, completes the event, records the result/audit, notifies the applicant, and moves the application to `awaiting_decision` only after every non-cancelled event has a result. Integration tests cover scheduling, result recording, multi-event completion and status transitions; HTTP guard tests cover method, CSRF and authentication checks. This does not implement rescheduling/cancellation or an authorized correction/revision history for a result. GET /api/notifications.php returns up to 100 newest notifications for the signed-in user only. POST /api/mark-notification-read.php accepts a positive integer `notification_id` and requires a current CSRF token; it only updates notifications owned by the signed-in recipient, is idempotent for already-read notifications, and writes an audit event on first read. MySQL integration tests cover recipient isolation, read-state persistence and audit logging; HTTP guard tests cover method restrictions, unauthenticated inbox denial and CSRF rejection. POST /api/upload-document.php accepts multipart form fields `application_id`, `document_type`, and `document` plus the current `X-CSRF-Token`. It is applicant-only, verifies ownership and editable application status, requires an active program requirement key, accepts PDF files up to 10 MiB by default (or a smaller per-requirement limit), checks server-detected MIME and PDF signature, generates a random storage key, writes a SHA-256 digest, records an audit event, and stores bytes only at `EQUIPATH_PRIVATE_STORAGE_PATH` outside the web root. Configure that path to a private writable directory not served by Apache/Nginx; uploads fail closed if it is missing. `EQUIPATH_MAX_UPLOAD_BYTES` can lower the default limit (maximum 10 MiB). GET /api/download-document.php?document_id={id} returns a PDF as an attachment to the owning applicant, an evaluator with a current assignment, or a coordinator while the application is in the screening/correction queue. It verifies the stored file size, PDF signature, and SHA-256 before sending bytes, uses no-store and anti-sniffing/frame protections, and writes a successful-download audit event before responding. Unauthorized access is denied and administrator access is not implicit. Automated MySQL integration tests cover owner and assigned-evaluator access, cross-applicant denial, administrator denial, integrity verification, and audit logging. Automated HTTP guard tests verify that GET is rejected and multipart POST without a valid CSRF token is denied before database access. A successful authenticated multipart upload and its rollback/cleanup paths still need end-to-end integration coverage. Antivirus scanning/content disarm also remains outstanding; do not use real applicant files or treat the feature as production-ready. Enforce HTTPS in deployed environments. The GET /api/health.php endpoint is a liveness check and deliberately returns database: not_checked without connecting to MySQL. GET /api/readiness.php is a separate database-readiness probe: it executes SELECT 1 and returns HTTP 200 with database: connected on success or HTTP 503 with database: unavailable on failure. Its response intentionally omits connection errors and credentials. Use readiness.php when checking database connectivity, but verify it against the actual hosted database; a passing CI test does not establish that hosting configuration is correct.

The public web page's sign-in flow obtains a CSRF token, submits credentials to the PHP authentication endpoint, refreshes the token after session rotation, and loads only notifications returned for the authenticated recipient. Mark-as-read uses the CSRF-protected endpoint. Notification titles/messages are inserted as text nodes (not HTML). This is a development UI slice, not a complete applicant/staff portal; it does not provide public registration, account recovery, email verification, application submission screens, or external email/push delivery. The page remains explicitly marked as a development build; do not submit real applicant records.

## Desktop stack (supplementary)

1. Install Visual Studio with the .NET desktop development workload and the .NET 10 SDK.
2. Open desktop/EquiPath.Desktop.csproj.
3. Start Apache and ensure the PHP API is available at http://localhost/equipath/api/health.php.
4. Run the desktop project and select Check PHP API.

The desktop client calls PHP instead of connecting directly to MySQL. This keeps database credentials out of the desktop binary and allows the PHP API to enforce the same business rules for both clients.

## Run tests

From the repository root:

    php -l web/api/health.php
    php -l web/public/index.php
    php tests/php/run.php
    php tests/php/schema_contract.php
    php tests/php/session_security.php\n    php tests/php/authorization_integration.php

For database integration tests, apply migrations 001 and 002 to a disposable MySQL 8.4 database and set DB_HOST, DB_USER, DB_PASSWORD, DB_NAME, and a random AUTH_RATE_LIMIT_SECRET of at least 32 characters. CI provisions an isolated MySQL service, applies both migrations, and runs database, authentication, authorization, session-security, login-throttling, screening, notification, document-upload input-validation, and authorized document-download integration tests automatically.

The initial schema covers configurable program requirements and approved credit records as well as application workflow data. The current database tests check table creation, unique email enforcement, and rejection of invalid foreign-key references. Authentication integration tests verify valid active-account credentials, wrong passwords, unknown email addresses, pending/disabled accounts, empty inputs, safe return values, and successful-login timestamps. They do not prove every workflow, authorization rule, concurrency case, backup, or restoration scenario.

## Important test gates before real use

Before enabling a workflow, add tests for the corresponding behavior:

- Authentication: credential-verifier tests cover valid/invalid credentials, pending/disabled accounts, unknown email, empty input, and safe return values. Session security primitives now cover session ID rotation, minimized identity storage, CSRF token validation, and session destruction. Still required: password reset, role/resource authorization, comprehensive endpoint tests, and operational recovery. HTTP authentication endpoints and database-backed login throttling are present as a development foundation but must not be treated as production-ready until reviewed and tested end-to-end.
- Authorization: `AccessControl` rechecks active account status and database-backed role membership at decision time. Applicants are restricted to their own applications; evaluators require a current assignment; other staff roles must be explicitly allow-listed by the calling endpoint. Administrator access is not implicit. The application listing endpoint now calls the policy for each returned application, and the MySQL authorization integration test exercises the real endpoint to verify it does not expose another applicant's application. Other protected workflows still do not exist and must enforce the relevant policy with endpoint-level tests before being enabled.
- Input and SQL: prepared statements; malformed IDs and payloads; server-side validation; invalid state transitions; duplicate submissions and concurrency.
- Evidence files: upload validation, randomized private storage, upload audit events, authorized attachment downloads, stored-file integrity checks, and download audit events are implemented. CI checks upload endpoint method and CSRF guards over HTTP; still required: successful authenticated multipart-upload and rollback/cleanup integration coverage, malware scanning or an approved manual scanning workflow, retention/deletion policy, and operational storage monitoring.
- Evaluation and decisions: rubric score bounds, required feedback, assignment constraints, approval provenance, immutable or versioned decision history.
- Database: migrations from clean and prior versions, constraint violations, transaction rollback, least-privilege DB user, backup and restore drill.
- Privacy and audit: audit events for sensitive reads/changes, no passwords/tokens/file contents in logs, retention/export rules confirmed with ADFC.
- Integration: malformed/duplicate registrar imports, validation reports, idempotent retries, and reconciliation of failures.
- Desktop client: API timeout, HTTP error, invalid JSON, unsupported API response, and no embedded database credentials.

## CI

GitHub Actions runs PHP syntax and smoke tests, validates the schema contract, applies both migrations to a clean MySQL 8.4 service, runs database integrity, credential-verifier, authorization, session-security, and login-throttling tests, and builds the WinForms project on Windows. Green CI is a required quality gate, not proof that the system is production-ready.
